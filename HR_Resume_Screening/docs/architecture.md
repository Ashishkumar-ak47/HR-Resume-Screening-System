# Architecture and data flow

## Directory responsibilities

- `include/` contains the shared structures, limits, return statuses, and function declarations.
- `src/main.c` parses command-line options, chooses the default or custom skill profile, invokes analysis, reports errors, and writes output.
- `src/employee.c` validates, adds, finds, lists, and removes local employee roster records. `main.c` invokes it for the `employee` command group.
- `src/module1.c` streams resume bytes, tokenizes words, and increments configured-skill frequencies.
- `src/module2.c` initializes skill sets, validates/loads profiles, calculates coverage, classifies the result, and formats reports.
- `src/utils.c` contains bounded token normalization and skill-name validation helpers.
- `test/` contains unit tests for the reader/utilities and analysis/profile/report modules.
- `data/` contains the local employee roster. It stores employee identity and resume path, not resume text.
- `sample/` contains a sample resume and role skill profile for a repeatable demonstration.
- `docs/` contains the requirements baseline, architecture, deployment, and test documentation.
- `build/` is generated output and is ignored by version control except for its placeholder.

## Processing flow

1. The regular screening CLI validates options and requires one resume path. The employee CLI can add/list/remove records or look up an employee for screening.
2. It initializes the built-in skills or loads a validated line-based skill profile.
3. The reader opens the resume and reads one byte at a time with a 5 MiB ceiling.
4. Alphanumeric characters form a token. A delimiter ends it; the helper lowercases it and the analyzer compares it to each profile entry.
5. The report counts distinct matched skills, computes equal-weight percentage coverage, sorts frequencies, and emits text.
6. If `--output` is supplied, a new file is created exclusively. Existing files are left intact.

Employee records are stored as delimited text in `data/employees.txt`; removal writes a replacement file then swaps it into place. Resume files are not deleted when a record is removed. The roster is unencrypted and has no authentication, permission model, audit trail, or multi-user locking, so it is for local POC use only.

## Memory and error model

No heap allocation is used. Skill names, token text, and sort indexes live in bounded arrays. Each open file has one close path, and read/write/close outcomes are checked. Status values are declared in `include/common.h`; user-facing error messages are generated by the CLI.
